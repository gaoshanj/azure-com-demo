合同订单管理系统 (COM)
Azure 目标架构设计

一套贯穿「下单 → 审批 → 归档」端到端的业务系统，作为《Azure 系统实战培训》的主线案例。 本文覆盖架构分层、Azure 服务选型、网络与身份设计、成本模型与治理策略，并对齐课程 9 个模块的讲解落点。

版本 v1.1 区域 East Asia 形态 教学级 PoC / 可演进到生产 课时 6h × 2 次 日期 2026-10-20

1.3 设计假设（需客户确认，见第 12 章）

  • 云环境：Azure Global（公有云），单区域 East Asia；中国区（21Vianet 运营）差异另附备注。
  • 身份源：以 Entra ID 云身份为主，不强制混合身份；企业 AD 同步仅作扩展讨论。
  • 部署形态：全部 PaaS，不使用 IaaS 虚拟机承载业务；VM/VMSS 仅作为「计算选型对比」与「Backup / ASR 演示」的配角资源。
  • 规模基线：日均订单 500 单、合同 PDF 日均 300 份、并发在线 50 人。教学级容量，非生产压测基线。
  • 数据合规：合同属于企业敏感数据，全程私有网络 + 静态加密；不引入跨境数据流动设计。
设计原则

① PaaS 优先——把运维复杂度留给平台，课堂演示聚焦「配置决策」而非「装机器」。

② 默认私有——所有数据面走 Private Endpoint，公网仅暴露 Web 入口。

③ 无密码优先——应用身份全部用托管标识，Key Vault 里不存应用密钥。

④ 决策可解释——每个服务选型都留「为什么不是另一个」，这正是学员最需要的部分。

⑤ 可整体销毁——全部资源打标签 + 单资源组，课后一条命令清理，成本可控。

02业务流程与状态机

2.1 主干流程：下单 → 审批 → 归档

03总体架构与分层

按大纲「经典三层架构（Web / App / Data）映射 Azure 服务」的要求，本系统严格保持三层边界，并在每层之间插入集成层与平台层两个横切面：

3.1 三层映射说明

逻辑层职责Azure 落地为什么不是别的
Web / 表现 页面渲染、登录跳转、API 网关式路由 App Service（Linux，B1 → P0v3） 不用 AKS：团队无 K8s 运维能力，教学场景也不需要编排收益；不用 Static Web Apps：需要与 API 同域、同 VNet 集成
App / 应用 业务规则、长耗时任务、流程编排 Functions（事件驱动）+ Logic Apps（审批编排） PDF/OCR 突发且空闲期长 → 按执行计费；审批是「可视化流程 + 长事务等待」，Logic Apps 的内置 Callback 动作天然适合「等人 48 小时」，且不引入第三方许可依赖
Data / 数据 事务一致性、文件对象、审计留痕、热点缓存 SQL + Blob + Cosmos + Redis + Files 订单/合同是强关系模型 → SQL；PDF 是大对象 → Blob；审计是追加型高写入 → Cosmos；缓存 → Redis
课堂上值得强调的边界

不要把「合同 PDF」放进 Azure SQL 的 varbinary(max)。合同单体 2–8 MB、年均 10 万份，塞进数据库会让备份体积、还原时间和 DTU 成本同时失控。数据库只存 BlobPath + SHA256 + 元数据——这是学员在真实项目里最常踩的坑之一。

4.1 关键选型决策记录（ADR）

这是课堂「识别关键决策点」的抓手——每条 ADR 都是一个可以现场展开讨论的取舍。

决策选型备选取舍理由
ADR-01
计算形态		App ServiceAKS / Container Apps / VM无集群运维负担；内置槽位切换与自动缩放；教学可解释性最强。规模到日均百万请求再评估 AKS
ADR-02
审批实现		Logic Apps（编排）+ 自有 Web 审批页（交互）Power Automate + Approvals 连接器 / 自研状态机 / Durable Functions客户无 Power Platform 许可，Approvals 连接器与 Teams 审批卡片不可用，故人工交互收敛到自有门户，Logic Apps 只用内置 Callback 动作「等结果」；保留可视化运行历史与超时分支，且审批数据不出本系统
ADR-03
消息中间件		Service BusStorage Queue / Event Grid需要死信、重复检测、会话有序、事务性发送——Storage Queue 只能解决「排队」；Event Grid 是通知而非任务队列
ADR-04
合同存储		Blob + 容器级不可变策略SQL varbinary / 第三方归档WORM 由平台保证，可出具合规证明；数据量线性增长不影响数据库性能
ADR-05
审计存储		Cosmos DB（可选）SQL 追加表 / Log Analytics追加写、按订单分区、TTL 自动过期；若客户已用 SIEM，可改用 Log Analytics 或直接投 Event Hub
ADR-06
凭据管理		托管标识 + Key Vault RBAC连接字符串 + 密钥零密钥落盘，轮换成本为零；这是 Security 模块最好的正面案例
ADR-07
数据库访问		Entra 认证（无 SQL 账号）SQL 登录名 + 口令与 ADR-06 一致；缺点是连接串需指定 Authentication=Active Directory Managed Identity

6.1 管理组与订阅层级

对应大纲「订阅 / 管理组 / 资源组的分层组织模型与边界」。策略与权限在最高可行层级授予，避免逐资源打补丁。

课堂金句

「能给资源组就别给订阅，能用内置角色就别写自定义角色，能用托管标识就别发密钥。」这三句话可以覆盖 80% 的 RBAC 现实问题。

别把业务权限塞进 RBAC

谁能审批某个订单，是业务规则，存在 ApprovalTask 与角色表里，由应用层代码校验；Azure RBAC 管的是「谁能配置这套系统」。两者混用会导致每次组织架构调整都要重发角色分配，还会让审批人被迫拿到不必要的云资源权限——这是权限治理里最常见的设计错位。本系统的审批人不持有任何 Azure 角色。

7.2 存储设计：容器、层级与 WORM

容器内容冗余访问层策略

WORM 的三个实操坑（课堂必讲）

① 只能加不能减：保留期一旦设定，只允许延长不允许缩短；策略锁定（Locked）后连删除策略都不行——所以演示环境务必用 Unlocked 状态。

② 与归档层冲突：不可变数据可以在 Hot/Cool/Archive 之间移动层级，但 Archive 层上的读取需先解冻，合规取证的 SLA 要提前对齐。

③ 容器级 vs 版本级：本设计用容器级（覆盖所有对象，更适合法务归档）；版本级适合混合内容容器。

notification-jobsQueueFunctions / Logic AppsFunctions（ACS 邮件 / IM Webhook）指数退避重试；死信告警

为什么 Topic 而不是三个 Queue：新增订阅方（如未来的计费系统）时，发布侧代码零改动。这是课堂上讲「发布-订阅 vs 点对点」的最短路径示例。

7.4 端到端时序（Approved 之后的异步链路）

#参与方动作失败处理
1API审批回调：InReview → Approved，写 DB，向 contract-jobs 投递作业DB 与消息不一致 → 用 Outbox 表补偿
2Functions取模板 + 订单数据，渲染 PDF，上传 contracts-active渲染异常 → 重试 5 次 → 死信 + 告警
3FunctionsOCR 回读 PDF 关键字段（金额、客户名、日期）与 DB 比对不一致 → 置 GenerateFailed，人工复核
4Functions写 Contract 记录（BlobPath + SHA256），状态 → Generated幂等键去重，避免重复合同
5Functions复制到 contracts-archive（不可变容器），写审计事件，状态 → Archived归档失败保持 Generated，由定时任务补偿
6Functions投递通知作业 → 邮件 / IM通知失败不影响主流程状态

SHA256 的作用值得单独讲一分钟：它让「归档后的合同」具备可验证的完整性证明——日后任何一方质疑文件被改动，重算摘要即可自证。

7.5 审批交互设计（Web 审批页 + 回调编排）

约束变更：不使用 Power Platform

客户未采购 Power Platform / Microsoft 365 许可，因此不使用 Logic Apps 的 Approvals 连接器、Power Automate 审批流、Teams 审批卡片。审批交互收敛到系统自有的 Web 门户，Logic Apps 只承担编排与「等人」。附带收益：审批数据不出本系统、不依赖第三方订阅、权限模型由应用自己掌控。

这里替换的是「人在哪里点按钮」，不是「流程怎么走」。Logic Apps 用内置的 Request / Wait for an HTTP request（Callback）模式实现「等人」这一步：

#参与方动作关键约束
1API订单提交后调用 Logic Apps 的 HTTP 触发端点，传入订单号、金额、条款类型托管标识取令牌调用；附 correlationId
2Logic Apps按金额 / 条款判定审批层级，生成签名回调 URL，进入等待动作（timeout 48h）回调 URL 由平台生成，一次性、带签名
3API创建 ApprovalTask，把回调 URL 加密存入 Key Vault（或加密列），仅 API 身份可读浏览器永远拿不到回调 URL
4Functions投递提醒邮件（ACS Email），正文只含「您有 1 条待办」+ 门户链接邮件仅提醒，不作审批凭证
5审批人登录门户 → 待办列表 → 订单详情 → 批准 / 驳回 + 意见Entra ID 登录；服务端校验业务角色与层级匹配
6API写审批记录 → 从 Key Vault 取回调 URL → 调用回调 → 工作流恢复幂等键去重；重复回调返回 409
7Logic Apps还有下一级 → 回到步骤 2；否则汇总结果并回调 API 更新订单状态超时分支：升级至上级或按策略转交

安全与可运维性要点

  • 回调 URL 是服务端凭据，不是链接：它等价于「批准这个订单」的能力，泄露即越权。因此只存 Key Vault、只由 API 调用，绝不回传前端。
  • 回调端点加 IP 限制：Logic Apps 侧配置「允许的入站 IP」，仅放行 NAT Gateway 出口 IP，形成签名 + 来源 IP 双因子。
  • 业务权限 ≠ Azure RBAC：审批人不需要任何 Azure 角色，审批资格由应用内角色表决定；Azure RBAC 只管「谁能改这套系统」。
  • 待办中心是唯一事实来源：邮件丢失只影响提醒，不影响流程；审批人随时可在门户看到全部待办。
  • 可替换性：若客户未来采购 Power Platform，只需把「等待回调 + 通知」两段换成 Approvals 连接器，编排主干不变——这是把交互与编排分离的直接收益。
课堂讲法

这一步最适合讲「PaaS 的能力边界与许可成本」：Logic Apps 本身不需要 Power Platform 许可，需要许可的是它调用的连接器。学员在真实项目里做选型时，往往只看了服务单价，没看连接器背后的订阅依赖——这类问题要到上线前才暴露。

讲清楚 RTO 与 RPO 的区别

RTO 是「多久能恢复业务」，RPO 是「会丢多少数据」。合同系统的 RPO 必须接近 0（不能丢已签合同），因此 SQL 依赖日志备份 + Blob 依赖多副本同步复制；而 RTO 可以放宽到数小时——这个不对称是架构设计的起点，不是运维的补救。

9.3 成本治理四件套

  • 标签策略：env（poc/dev/prod）、costCenter、owner、app=com。在管理组层用 Policy Require tag，缺标签拒绝创建——这比事后催补标签有效得多。
