模块设计、技术栈与部署方案

这份文档是架构设计（v1.1）的落地契约：把"图上的 21 个资源"拆成可独立开发、可独立验证的 11 个模块，锁定技术栈，并给出可重复执行的部署路径。目标是在授课现场有一套真实运行、可点击、可解释的系统，而不是幻灯片上的框图。

版本 v2.1 已部署 20/20 区域 East Asia 订阅 Visual Studio Enterprise 运行时 .NET 8 部署 Bicep + 脚本 前置文档 架构设计 v1.1

01交付策略与设计基线

整件事有三个约束，它们直接决定了后面的每一个取舍：明天要讲、客户现场演示不能崩、预算要能说清。因此本次交付不是"先写完再跑"，而是本地可跑 → 云端可跑 → 现场可演三层验证。

基线项取值说明
架构基线架构设计 v1.1 的 21 项资源清单与三条 ADR 主干不新增服务，不删课程点；偏离处必须在此文档登记
业务主线建单 → 提交 → 多级审批 → 合同 PDF 生成 → WORM 归档 → 通知同步链路在"提交"截断，PDF/OCR/通知全部异步
许可边界无 Power Platform 许可审批用自有 Web 门户 + Logic Apps HttpWebhook 回调
云环境Azure Global（非 21Vianet）已确认 AzureCloud，区域 East Asia
代码形态单仓库、双应用、可本地全量运行本地用 SQLite + 文件系统 + 进程内队列，云端切 Azure 实现
这套 PoC 的定位

它是教学载体，不是产品。判断标准不是"功能全不全"，而是每个课程模块都能在界面上找到一个可点击的落点：讲网络能点开 PE，讲身份能点开托管标识，讲成本能点开预算。所以宁可砍功能，不可砍"可观察性"。

三条贯穿全局的设计原则

Principle 01
同一份代码，两种宿主
每个 Azure 依赖都有本地替身（SQLite / 文件系统 / 进程内队列）。本地跑通再上云，故障面从"云 + 代码"收敛为"代码"。
Principle 02
降级优先于完美
私有端点、Functions 异步、Redis 都是可降级项。演示前若某项不通，改一个 app setting 即回退，绝不现场改代码。
Principle 03
基础设施即讲解材料
Bicep 按课本章节分模块，部署日志本身就是教学素材：谁依赖谁、哪一步耗时最长，都能在现场展示。

一处与架构文档的偏离，先登记

3.1 审批模块：三级分档 + Webhook 回调

审批是整套系统的"剧情核心"，也是唯一跨越三个 Azure 服务（API / Service Bus / Logic Apps）的链路。规则很朴素，但每一层都要能讲清"为什么放在这里"。

订单总额（含税）审批层级审批角色路由理由
< ¥500,0001 级approver1 销售总监常规额度，单人可决，追求时效
¥500,000 – ¥2,000,0002 级approver1 → finance跨部门：业务先确认可行性，财务再确认回款风险
≥ ¥2,000,0003 级approver1 → finance → admin重大金额，逐级会签，任一级驳回即终止

编排用 Logic Apps 的 HttpWebhook 动作，而不是轮询。这是本方案里最值得在课上展开的一段，因为它同时讲清了"PaaS 编排的持久化能力"和"服务端凭据的边界"：

API 提交订单，调 Logic Apps 触发端点
载荷只有 orderId / level / amount / approverUpn，不含业务数据副本，避免两份真相。
工作流进入 HttpWebhook，向 API 的 /internal/webhook/subscribe 注册
Logic Apps 把本次运行的回调 URL 交给 API；API 把它写到该审批任务的记录上（生产应入 Key Vault，PoC 简化并注明）。
工作流挂起等待，最长 48 小时
挂起期间不占计算资源、不计长时间运行费用——这是 Logic Apps 相对自建轮询的核心价值，也是现场最容易讲出"哦"的一点。
审批人在门户点"批准"
API 落库 → 读回调 URL → POST 恢复工作流 → 工作流继续执行业务动作。
还有下一级则再起一个实例，否则更新订单状态
每级一个运行实例，运行历史天然成为"审批过程可追溯"的证据链。
安全要点（课上必讲）

回调 URL 等价于"批准这个订单"的能力，它本身就是凭据。三条铁律：只存服务端、只由 API 调用、绝不回传浏览器。传输上加共享密钥头 + 来源校验，形成双因子。业务审批权限由应用内角色表判定，审批人不持有任何 Azure RBAC 角色——业务权限与平台权限必须解耦。

3.2 合同归档：PDF 为什么不进数据库

合同 PDF 平均 200–400 KB，进 SQL 会带来三个后果：备份体积膨胀、查询缓冲池被污染、版本管理没有原生能力。所以库里只存指针 + 摘要 + 不可变截止时间，文件进 Blob 的 contracts 容器并施加保留策略。

Integrity
SHA256 摘要
入库时算摘要写进 SQL。事后核对只需重算 sha256，一行命令证明"文件没被换过"。
Immutability
WORM 保留策略
容器级 time-based retention。PoC 用未锁定策略（可解除，便于清理），课堂上演示"锁定后连管理员也删不掉"。
Access
短时 SAS
下载走 5 分钟只读 SAS，不暴露存储密钥；容器本身关闭匿名访问。

3.3 OCR 录入：把"不确定"显式化

现场最容易被问倒的地方是"抽取不准怎么办"。所以设计上不追求全自动建单：抽取结果一律落到草稿，逐字段带 confidence 与 source（模拟 / Document Intelligence），置信度低于 0.8 的字段在界面上高亮待人工确认。这条比"AI 准确率 99%"更能说服客户——它承认了现实。

05技术栈与选型理由

选型原则只有一条：课堂上看得到的部分用最直白的技术，课堂上看不到的部分用最省事的技术。所以前端不引框架（现场能直接改一行 CSS 给客户看），后端用 Minimal API（路由与处理函数在同一屏内，好讲）。

层次选型为什么是它为什么不是另一个
语言/运行时.NET 8 (LTS) · C# 12App Service / Functions 一级支持；单一语言贯穿 API 与 Worker，代码可共享不用 Node：PDF 中文字体渲染在 Linux 上坑更多
Web 框架ASP.NET Core Minimal API端点即函数，一个文件能读完一条链路，适合投屏讲解不用 MVC 分层：控制器+服务+DTO 会稀释重点
前端原生 HTML/CSS/JS（无构建）零构建链、零 npm 依赖、现场可直接改；单文件可读不用 React/Vue：为演示引入构建失败风险不值得
ORMEF Core 8（双提供程序）同一模型可跑 SQLite（本地）与 Azure SQL（云）；EnsureCreated 免迁移工具链不用 Dapper：多一层手写 SQL，本地/云端差异更大
认证Bearer JWT（HS256）+ 角色策略无 Cookie → 无跨站 SameSite 问题，前后端分域部署更稳不用 Cookie 会话：web/api 两个域名下会翻车
PDFQuestPDF（Community）纯托管、Linux 原生、中文字体可控、无浏览器依赖不用 wkhtmltopdf/Playwright：容器镜像大、字体缺失
可观测OpenTelemetry → App Insights一行 UseAzureMonitor 接通；traceId 贯穿 API→队列→Functions不用自建日志：客户要看的正是托管能力
IaCBicep（模块化）Azure 原生、无状态文件、what-if 可预览；模块对应课程章节不用 Terraform：多一个 state 后端要解释
异步Service Bus + Functions需要死信、重复检测、会话有序——队列语义比"能跑通"更重要不用 Storage Queue：无死信子队列，讲不出重试策略

5.1 一个反直觉的实测结论

架构文档里写的是 "B1 → P0v3" 的演进路径。我把 East Asia 的实际零售价拉出来核对，发现这个路径在东亚区是错的：

$137.6/月

$14.5/月

结论

本 PoC 选 S1：它是"支持 VNet 集成"这一能力线上的最低价档位，同时附带部署槽（可讲灰度）。P0v3 的溢价在东亚区买不到课堂需要的任何额外能力。
这条正好是课上"不要用'新旧'判断成本，要用价格 API 判断"的现成案例——我把它写进文档而不是藏起来。

06关键实现约定

6.1 适配层：每个 Azure 依赖一个接口 + 两个实现

6.2 幂等：提交只做一次

提交订单会触发审批链与工作流启动，重放代价高。做法是 Order.IdempotencyKey（前端生成 UUID）+ 唯一索引：重复提交直接返回首次结果，不再启动第二个工作流。课上讲"为什么不该用 GET 做状态变更"时，这是现成的正例。

6.4 零密钥

所有 Azure 访问走 DefaultAzureCredential：本地是开发者登录，云端是系统分配托管标识。Blob/SB/SQL/Cosmos 全部关闭本地密钥认证（sharedKeyAccess: false、localAuthDisabled: true），SQL 用 Entra 认证 + 托管标识建库用户。这样"密钥泄露"这类风险在架构上被消除，而不是靠流程约束。

08部署方案

采用 Bicep 分模块 + 脚本编排 + 三阶段推进。不用 azd（需要额外安装且模板约定会遮挡细节），不用 GitHub Actions（明天上课，本地直推最快；CI 作为课后延伸讲）。

8.1 为什么分三阶段

一次性部署 20 个资源，失败后定位成本高。分阶段后每段都有明确的验证点，且前一段失败不会污染后一段。

阶段内容耗时验证动作现场价值
P1 基础RG、VNet×2、子网、NSG、对等、私有 DNS 区、Storage、Key Vault、SQL、App Service Plan + 2 应用6–9 minGET /healthz = 200；门户能登录网络模块的所有静态素材（IP 规划、NSG、对等）
P2 集成Service Bus、Private Endpoint ×4 + 私有 DNS 记录、关闭公网访问、Functions、Logic Apps、Cosmos、ACS8–12 minGET /api/ops/deps 四项全 greenPE 连接状态、私网解析、运行历史
P3 治理Log Analytics 告警规则、预算、Policy 分配、标签补全2–3 min门户"成本管理 → 预算"可见；告警规则已启用⑧⑨ 监控与成本治理
阶段划分的真正原因

P2 会关闭 SQL/Blob/KV 的公网入口。这一步一旦执行，本机就再也连不上数据库——所有后续操作必须从应用内部发起（应用有 VNet 集成）。因此必须先把应用跑起来、把建表与种子数据在 P1 完成，再在 P2 收网。这个顺序本身就是课上"先连通、再收紧"的方法论。

12.3 与设计稿的九处偏差

设计稿是意图，部署结果是事实。偏差不分对错，只有原因和代价。这几条如果客户问"能不能不这样"，答案就在最右列。

编号设计稿写法实际做法为什么改（课堂讲点）
D-01Service Bus 也配 Private Endpoint不建 PE，改公网入口 + disableLocalAuth + 仅托管标识授权Standard SKU 不支持 PE，会直接报 PrivateEndpointInvalidSku；PE 要 Premium，月费从 $10 跳到约 $677。知识点 PE 不是"所有 SKU 都有"的通用能力。
D-02Cosmos DB 与其它资源同区域落到 Southeast Asia，通过 cosmosLocation 参数控制East Asia 返回 ServiceUnavailable: high demand，是区域容量而非配额问题。审计镜像对延迟不敏感，跨区约 +35ms 可接受。知识点 区域容量不足是新订阅最常见的"莫名其妙失败"。
D-03预算 startDate 固定为年初utcNow('yyyy-MM-01')，且必须声明成参数默认值月度预算要求起始日不早于当月，写死历史日期报 400；而 utcNow() 在 Bicep 里只能出现在参数默认值位置，不能写在资源里（BCP065）。
D-04dotnet publish 默认参数加 -r linux-x64 --self-contained false不指定 RID 会把 Windows/macOS 的原生库一起打包，175MB → 65MB，zip 85MB → 35MB。目标只有 App Service Linux，其余平台纯属浪费部署时间（也是 SCM 超时的诱因之一）。
D-05Blob 探针用 BlobServiceClient.GetPropertiesAsync()改为读容器属性前者是管理面调用（?restype=service&comp=properties），只授予 "Storage Blob Data Contributor" 的托管标识会被 403。结果是"存储明明是通的，探针却报红"。典型 数据面角色 ≠ 管理面权限。
D-06先上传，再 SetMetadata 补 sha256先算摘要，一次 UploadAsync 连元数据写入WORM 容器一旦写入就不能再改，"上传后补元数据"会被不可变策略拒绝。知识点 开了 WORM 之后，写入必须"一次成型"。
D-07Web 应用也挂全套业务 APIWeb 角色只服务静态门户 + /config.json同一个发布包靠 APP_ROLE 分角色；不加判断的话 Web 应用会对外暴露一套连着空库的 API，既浪费攻击面又容易在演示时被误访问。实测 GET /api/orders 在 Web 域名上返回 404。
D-08把 .bicep 直接交给 az 编译先用 bicep CLI 编成 ARM JSON 再提交az 调用的 ~/.azure/bin/bicep.exe 是 0 字节文件（下载中断的常见结果），报错是 [WinError 193] 不是有效的 Win32 应用程序——完全看不出根因。显式编译后错误可读、还能用 azd 自带的 0.36.1。
D-09Service Bus Data Owner 角色 GUID 记为 …3ce6f3185d4d修正为 090c5cfd-751d-490a-894a-3ce6f1109419部署直接报 RoleDefinitionDoesNotExist。教训 内置角色 GUID 不要凭记忆写，先 az role definition list --name "<角色名>" 查一遍。

12.4 课堂可以直接讲的"九个坑"

如果时间只够讲一页 PPT，就讲这一页——每一条都有现场可复现的证据：

#现象真相
1建 PE 报 PrivateEndpointInvalidSkuService Bus 的 PE 只属于 Premium。设计阶段的"全部走 PE"要按 SKU 逐项核对。
2Cosmos 建不出来，报 "high demand"不是配额、不是权限，是区域容量。换邻近区域即可，不必开工单。
3预算报 400 "start date prior to current month"月度预算的 startDate 必须落在当月或之后。
4az bicep 报 WinError 193内置 bicep 是 0 字节文件。别去查权限，先 ls -la 看大小。
5App Service 部署卡在 "Starting the site…" 200 秒Linux 容器首次拉起 + 大包解压。压包（D-04）能明显缩短，必要时改用 --type zip 的 OneDeploy。
6探针报红但服务其实是好的探针用了管理面 API（D-05）。可观测性自己也会撒谎，探针要选对接口。
7WORM 容器写入后改元数据失败不可变策略的语义就是"不可改"。写入要么一次成型（D-06），要么另存新版本。
8Key Vault 引用 @Microsoft.KeyVault(...) 能否跑在私有端点上能，前提是 WEBSITE_VNET_ROUTE_ALL=1 + WEBSITE_DNS_SERVER=168.63.129.16 + 私有 DNS 区已链接到集成 VNet。三个条件缺一不可。
9角色分配报 RoleDefinitionDoesNotExist内置角色 GUID 记错了（D-09）。GUID 不要背，要用命令查。

12.5 部署耗时实测

阶段耗时说明
基础设施（--infra-only）2–5 分钟第二次起为增量部署，比首次快一倍
API 部署4–10 分钟多数时间花在 "Starting the site"，不是上传
Web 部署4 分钟同上
Function 部署2 分钟zip deploy 202 后异步生效
全量（首次）约 25 分钟含一次失败重试；无错情况下约 15 分钟
现场提醒

冷启动后的第一个请求可能返回 500（SQL 连接池与 EF 模型首次构建）。演示前先用 verify.py 或浏览器把主流程点一遍"预热"，别让第一个动作就撞在冷启动上。

12.6 一键操作

# 全量部署（首次）
./infra/deploy.sh --subscription <sub-id> --location eastasia --name com-poc --profile full

# 只重建基础设施 / 只重发代码
./infra/deploy.sh --name com-poc --infra-only
./infra/deploy.sh --name com-poc --publish-only

# 只预览变更，不落资源
./infra/deploy.sh --name com-poc --what-if

# 端到端验收（20 项）
python infra/verify.py https://app-com-poc-api-ilvufq.azurewebsites.net

# 清理（先解 WORM 策略，再删资源组，最后 purge Key Vault）
./infra/teardown.sh --name com-poc --location eastasia --dry-run   # 先看清单
./infra/teardown.sh --name com-poc --location eastasia --yes
讲完就清

这套环境按需运行约 $2.5–3.5 / 天（S1 计划 + SQL S0 + Service Bus Standard + Cosmos Serverless + PE ×3）。teardown.sh 会先解除未锁定的 WORM 策略再删资源组——如果哪一步忘了，存储账户会一直挂着按量计费。讲完当天务必执行。
